## 1. What this is

James asked for an Obsidian-class notes app, native for macOS 26 and iOS 26,
following current Apple design language. Requested feature set:

- Vaults, multi-vault, cross-device sync via **iCloud or GitHub**

- Elegant, minimal design
- **en / 简体中文 / 繁體中文** switching

## 2. Architecture, and why

```
Inkstone.xcodeproj          generated by XcodeGen from project.yml (gitignored)
├── App/                    SwiftUI app, ONE target for both macOS and iOS
│   ├── InkstoneApp.swift   scene, menu commands, resolved Style environment,
│   │                       DEBUG test hooks (see §5)
│   ├── Model/
│   │   ├── Workspace.swift    central app state: vault, index, tabs, history,
│   │   │                      link following, file actions, daily notes
│   │   └── NoteDocument.swift live text buffer, debounced autosave (700ms),
│   │                          external-change reload
│   ├── Support/ThemeBridge.swift   Theme/Typography → SwiftUI + AppKit/UIKit
│   └── Views/              Sidebar, Editor, Graph, Canvas, Calendar, Settings,
│                           QuickSwitcher, RootView
└── Packages/InkstoneCore/  platform-agnostic engine, NO SwiftUI
    ├── Vault/     Vault, VaultRegistry, VaultScanner, VaultWatcher, NoteStore
    ├── Markdown/  Frontmatter, SyntaxScanner, NoteParser
    ├── Index/     IndexSnapshot, IndexBuilder, LinkRewriter
    ├── Search/    fuzzy quick-switch + full-text with tag:/path: operators
    ├── Graph/     GraphData + deterministic force simulation
    ├── Canvas/    JSON Canvas 1.0 model
    └── Settings/  Theme, Typography, AppSettings
```

Decisions that are load-bearing — don't undo them casually:

**Files on disk are the only source of truth. No database.** A vault is a plain
folder; Obsidian can open an Inkstone vault and vice versa. App-specific state
lives in a hidden `.inkstone/` folder. The direct consequence: renaming a note
*must* rewrite `[[links]]` across the vault (`LinkRewriter`), because with no
database a broken link is permanent. That's implemented and tested.

**`InkstoneCore` has no UI framework dependency** — Foundation + Yams only. So
parsing/indexing is unit-testable with `swift test`, no simulator, no Xcode. This
is why the engine could be verified even while the GUI was unrunnable.

**One target for both platforms** via XcodeGen `supportedDestinations`, with
`#if os(macOS)` splits confined mostly to `MarkdownEditorView.swift`.

**The editor wraps NSTextView/UITextView, not SwiftUI `TextEditor`.** We need
attributed-run access, caret position, click targets on links, and TextKit
paragraph metrics. `TextEditor` exposes none of that.

**Live preview technique:** syntax markers (`**`, `[[`, `#`) are collapsed by
setting a 0.01pt font + clear colour on the delimiter ranges; the paragraph
containing the caret is exempted so syntax reappears on the line you're editing.
See `MarkdownHighlighter.highlight(_:caretLineRange:)`.

**Canvas uses the open [JSON Canvas 1.0](https://jsoncanvas.org) spec**, so
`.canvas` files round-trip with Obsidian losslessly.

**GitHub sync was re-planned before being written.** libgit2 on iOS is a swamp;
the plan is the GitHub Contents API with a local shadow index instead of real git.
Nothing implemented yet.

**CJK-Latin spacing (盘古之白) is a rendering-time kern**, never a text edit — the
file on disk is untouched. `MarkdownHighlighter.applyCJKLatinSpacing`.

## 4. THE OPEN BUG — read this first

**Symptom:** James clicked "Open Folder as Vault", picked a folder, app died
instantly. `SIGABRT`.

**Crash report:** `~/Library/Logs/DiagnosticReports/Inkstone-2026-08-15-210222.ips`

Faulting thread is `com.apple.RenderBox.Device`:

```
libsystem_c.dylib    abort
RenderBox            RB::precondition_failure(char const*, ...)
RenderBox            RB::(anonymous namespace)::load_library(NSBundle*, id<MTLDevice>)
RenderBox            RB::Device::preload_resources()
RenderBox            RB::Device::Device(RBDevice*, id<MTLDevice>)::$_7::__invoke(void*)
```

**Zero frames of Inkstone code.** RenderBox is SwiftUI's Metal rendering backend;
it aborts while loading a shader library. The same signature appears in WebKit bug
302212, caused by a *system* `.metallib` failing to load.

Meanwhile the main thread was doing ordinary text layout
(`NSCoreTypesetter _getLineMetricsForRange:`) — it hadn't even finished a frame.

**The timeline is the useful part:**

```
20:14:36   process launched
21:02:01   crash          ← 47 minutes idle in between
```

47 minutes on the Welcome screen was fine, because Welcome needs no Metal. The
moment the vault UI appeared — sidebar materials, `.listStyle(.sidebar)`,
`.inspector` — SwiftUI created its **first** Metal device, and `RB::Device`
construction aborted.

**Environment finding, probably the actual cause:**

```
Physical display: OFF since 2026-08-12
Session: Screen Sharing (screensharingd + ScreensharingAgent, connected ~21:00)
```

The Mac's physical display had been asleep for three days; James was driving it
remotely over Screen Sharing on a virtual display. SwiftUI's Metal shader preload
failing under a headless/screen-shared display configuration fits every fact,
including why **only Inkstone crashed** — of the 3 recent crash reports on that
machine, only this one touches RenderBox, because most apps never hit that path.

**Confidence: hypothesis, not proven.** It was never reproduced.

### Why it couldn't be reproduced

Every avenue was blocked, in this order:

1. `screencapture` → "could not create image from display"
2. peekaboo → no Screen Recording / Accessibility grant, fell back to local host
3. Launching the binary directly → app never activates, no window, `.onAppear`
   never fires, only 3 threads and no render threads
4. `open`-launched app → discards stdout/stderr, so debug prints vanish
5. `defaults write com.orris.inkstone` → redirected into the sandbox container,
   which the shell can't write (`Operation not permitted`)
6. `~/Documents` → TCC-blocked for an unsandboxed dev build
7. Sandbox container → shell can't read it either (`Operation not permitted`)
8. `log show` → no retained entries for the crash window

### Next steps to resolve it

1. **Cheapest decisive test:** run it on a real, awake display — physically at the
   machine, or with a monitor attached. If it survives, it's the display/Metal
   environment and not the app.
2. If it still crashes, bisect the two build variables. An unsandboxed,
   no-hardened-runtime variant is already wired up:

   ```bash
   xcodebuild -project Inkstone.xcodeproj -scheme Inkstone \
     -destination 'platform=macOS' -configuration Debug -derivedDataPath .build-dev \
     build CODE_SIGN_ENTITLEMENTS=App/Resources/Inkstone-Dev.entitlements \
     ENABLE_HARDENED_RUNTIME=NO
   ```

   Sandbox on/off × hardened runtime on/off = 4 cells; the crash either follows a
   variable or it doesn't.
3. If it's confirmed environmental, the mitigation worth considering is reducing
   the Metal surface in the vault UI (materials/blur in sidebar and toolbars) so
   an OS-level bug can't take the app down. That's a design tradeoff — ask first.
4. Also worth filing as Feedback to Apple if reproducible on a real display.

## 5. Test harness (DEBUG builds only)

The macOS file picker is a separate process and can't be scripted, which makes the
entire post-open UI untestable. `InkstoneApp.openLastVault()` has DEBUG-only hooks
to bypass it. In priority order:

| Hook | How | Works under sandbox? |
| --- | --- | --- |
| Scratch vault | `INKSTONE_SCRATCH_VAULT=1`, or create the marker file at `Application Support/inkstone-scratch-vault` | ✅ yes — seeds a small vault inside the app's own container |
| Explicit path | `echo /path/to/vault > /tmp/inkstone-test-vault` | ❌ no — sandbox blocks `/tmp` |
| Env var | `INKSTONE_OPEN_VAULT=/path/to/vault` | ❌ no, and `open` doesn't forward env |

Debug output goes to stderr **and** to
`Application Support/inkstone-debug.log` inside the container, because `open`
discards stderr.

`VaultRegistry.register(folder:)` deliberately tolerates bookmark-creation
failure (falls back to a path-only vault) so unsandboxed dev builds work.

**Remove or gate these before shipping.** They're `#if DEBUG` already.

## 6. Environment gotchas hit this session

**Xcode 26.6 was broken.** A stale
`/Library/Developer/PrivateFrameworks/DVTDownloads.framework` (dated Feb 27)
shadowed Xcode's own copy, so `xcodebuild` couldn't load `IDESimulatorFoundation`
and refused to build *anything*. Fixed with `sudo xcodebuild -runFirstLaunch`.
If the second machine shows the same symptom, that's the fix.

**iCloud entitlement is deliberately disabled.** `iCloud.com.orris.inkstone`
doesn't exist in the developer portal, and enabling the entitlement before the
container exists makes every local build fail to sign with "requires a
provisioning profile". The keys are commented in
`App/Resources/Inkstone.entitlements` with restore instructions.
`WelcomeView.createICloudVault()` shows an alert instead of failing silently.
**Create the container in the portal first, then uncomment.**

**`DEVELOPMENT_TEAM: K9YT36SP4B`** (Orris Technology) is committed in
`project.yml`. Team IDs aren't secret — they appear in every notarised app — and
keeping it means the second machine builds immediately. Change it if building
under a different team.

- ~~**The app has no icon.**~~ Fixed 2026-08-16. `Tools/generate-app-icon.py`

in `Dictionary` iteration order, which varies per process — so graph layout
differed on every launch. Now iterates a sorted `orderedIDs`. A unit test caught
this; the test was right and the code was wrong.

## 8. Getting started on a new machine

```bash
git clone git@github.com:iamzifei/inkstone.git
cd inkstone

brew install xcodegen          # the .xcodeproj is generated, not committed
xcodegen generate

# engine only — no Xcode needed, fastest feedback loop
cd Packages/InkstoneCore && swift test && cd ../..

# macOS app
xcodebuild -project Inkstone.xcodeproj -scheme Inkstone \
  -destination 'platform=macOS' -configuration Debug \
  -derivedDataPath .build-xcode build
open .build-xcode/Build/Products/Debug/Inkstone.app
```

Then **Open Folder as Vault** → pick `Samples/Inkstone Demo` (committed in this
repo: interlinked notes, CJK tags, a callout, a table, an unresolved link, a
canvas). The sandbox has no standing access outside its container, so that manual
pick is the grant; the security-scoped bookmark restores it on later launches.

Typecheck both platforms without Xcode:

```bash
B=Packages/InkstoneCore/.build/arm64-apple-macosx/debug/Modules
CY=Packages/InkstoneCore/.build/checkouts/Yams/Sources/CYaml/include/module.modulemap
swiftc -typecheck -swift-version 6 -target arm64-apple-macos26.0 \
  -sdk "$(xcrun --sdk macosx --show-sdk-path)" -I "$B" \
  -Xcc -fmodule-map-file="$CY" $(find App -name '*.swift')
```
